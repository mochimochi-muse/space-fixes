## 1. 要注意の食い違い：「変化なしの日は何も送らない」と（A）

旧本文の手順5「変化が1つもなければ何も送らない（ユーザーの指示：変化なければ報告なし）」（2026-11-07の本人の指示）と、（A）の「値を報告に含めるだけ」を組み合わせると、**変化なしの日は、もちに何も届かない**。いまのGitHubメモ「GitHub（日付 9:12確認）：変化なし」を毎日出すための材料がなくなる。

### 解決案の比較

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|
| 案1：状態ファイルから作る | 状態ファイル `github-watch-state.md` に「最終確認：日時｜結果」の1行を足させ、もちはそこから GitHubメモを作る | 新しいファイルを増やさない | 状態ファイルは今「リポジトリ名｜SHA｜コミット日時」だけの形で、手順1に「書式が想定と違う場合は作り直し、何も送らずに終了（基準作りのみ）」という決まりがある。行の種類を足すと、のちの実行が「書式が違う」と判断して基準を作り直し、**変化を1回見落とすおそれ**がある。また、状態ファイルには「どのリポジトリが変化したか」が残らない（SHAとコミット日時だけ）ので、変化ありの日のメモ文面を作るには、さらに書き足しが要る |
| 案2：変化なしでも1行送る | 変化なしの日も「GitHub：変化なし」と1行だけ報告する | もちに必ず届く。仕組みが一番単純 | 2026-11-07の本人の指示「変化なければ報告なし」を変えることになり、**本人の承認が要る**。毎朝チャットに1行増える |
| **案3：値ファイルに残す（推奨）** | チェックが正常に終わったら、変化の有無にかかわらず、小さな値ファイル（JSON）を `~/workspace/goals/github/hidden_files/tracker-pending/` に書く。チャットへの報告は従来どおり変化があった日だけ。もちは値ファイルから GitHubメモを作る | 本人の指示（変化なしなら報告なし）をそのまま守れる。状態ファイルの形に触れない。朝のGmail要約ジョブと同じ置き方・同じ考え方（`01` 参照）なので、もちの手順と週次棚卸しの点検が1つで済む。反映し損ねても、ファイルが残っているので後から測り直し不要で反映できる（退避を兼ねる） | もちがチャットの報告をきっかけに動く場合、変化なしの日はきっかけがない。→ もちの手順（04）で「トラッカー用の値を処理するときは、両方の tracker-pending フォルダを必ず見る」と決めておき、翌朝の Gmail要約の受け取り時などに拾う。GitHubメモは最大1日遅れで反映されるが、画面には「◯日前の情報」と出るので古さは隠れない |

### 推奨：案3
- 本人の指示を変えずに済み、状態ファイルの「書式違いで基準作り直し」の危険にも触れない。
- 本文には「値ファイルの書き込みに失敗した場合だけ、変化なしの日でも1行送る」を入れた。これは手順7（失敗時は報告）と同じ「失敗の知らせ」の扱いで、指示の趣旨（変化がないのに毎日通知が来ないこと）は守られる。
- **本人の判断が要る点（未確定）**：

  - GitHubメモが「最大1日遅れ」で反映されることを許容するか（嫌なら案2を本人に提案する）。

```text
ユーザーの希望（2026-11-07）に基づく、GitHub（Kou52-Work）の定期チェック。読み取り専用。GitHubへの書き込み（コミット、コメント、Issue作成など）は一切しない。

priconne-daily-macro / login-bonus-auto / school-doc-automation / shiryo-tool / school-ledger-review / tsukin-keirozu / chatgpt-retry-assistant

手順：
1. 状態ファイル ~/workspace/goals/github/hidden_files/github-watch-state.md を読む。各リポジトリの「最後に確認した最新コミットのSHAと日時」が記録されている。

4. 報告（変化があった場合のみ）：メインチャットに日本語で簡潔にまとめる。リポジトリごとに「何が変わったか（コミットの要約）」「引き継ぎメモ上の現在地の変化があればそれ」を箇条書きにする。憶測で補わない。
5. 変化が1つもなければ何も送らない（ユーザーの指示：変化なければ報告なし）。
6. 最後に状態ファイルを各リポジトリの最新SHAと日時で更新する。
7. チェック自体が失敗した場合（接続エラー等）は、状態ファイルを更新せず、失敗した旨と理由を簡潔に報告する。ただし一時的な失敗を大げさに扱わない。

トラッカーダッシュボードのGitHubメモ用の値（2026-11-17追加の自動更新を、2026-11-23に改訂。改訂の理由：2026-11-22に本人が決めた恒久対応（A）により、このジョブはトラッカーダッシュボード（Space、slug: toratukadatusiyubodo）に書き込まない。結果を値ファイルに残し、ダッシュボードへの反映はもち（メインのチャット）が行う）：
- このジョブでは、トラッカーダッシュボードの getSnapshot・saveSnapshot をはじめ、Spaceの操作（artifact の操作）を一切行わない。capturedAt の更新もしない。
- チェックが正常に完了したら（手順1で基準作りだけをした回と、手順7の失敗時は除く）、変化の有無にかかわらず毎回、手順6のあとに、値ファイル ~/workspace/goals/github/hidden_files/tracker-pending/{今日の日付（JST）YYYY-MM-DD}.json を次の形で書く。フォルダがなければ mkdir -p で作る。同じ日付のファイルがあれば上書きする。下の値は書式の例であり、実際には今回の結果を入れる。
  {"source": "github-daily-check", "formatVersion": 1, "runDate": "2026-11-23", "checkedAt": "2026-11-23T09:13:05+09:00", "result": "unchanged", "changedRepos": [], "note": "GitHub（2026-11-23 9:12確認）：変化なし"}
  - checkedAt は値ファイルを書く時点の現在時刻（JST、ISO形式・+09:00付き）。今日の日付はシェルの `TZ=Asia/Tokyo date +%F` で確かめる。
  - result は、変化があれば "changed"、なければ "unchanged"。changedRepos は変化があったリポジトリ名の配列（変化なしなら空配列）。
  - note の文面：変化があった場合は「GitHub（{YYYY-MM-DD} 9:12確認）：変化は {変化があったリポジトリ名を列挙} の{N}リポジトリ」、変化がなかった場合は「GitHub（{YYYY-MM-DD} 9:12確認）：変化なし」。今回のチェック結果だけに基づいて書き、過去の結果を混ぜない。
- 変化があった日（手順4で報告を送る日）は、報告の一番最後に次の2行を足す（{note} は値ファイルの note と同じ文面）：
  【トラッカー用の値】
  GitHubメモ：{note}
- 変化がなかった日は、手順5のとおりチャットには何も送らない（2026-11-07のユーザーの指示を維持）。値ファイルだけを書く。
- 値ファイルの書き込みに失敗した場合：変化があった日は、報告の【トラッカー用の値】の2行の後に「値ファイル：書き込み失敗」と1行足す。変化がなかった日は、「GitHubチェックは変化なし。トラッカー用の値ファイルを書けませんでした」と1行だけ報告する（失敗の知らせとして、この場合に限り変化なしでも1行送る）。エラーの詳細は載せない。

正確さのルール（2026-11-10追加。コドモン献立表の誤読事故を受けた一般化）：
- コミットメッセージや引き継ぎメモの内容は、原文の表現に基づいて書く。要約で原文にない進捗・判断・数値を作らない。
- 「現在地」「次の作業」「判断事項」は、引き継ぎメモに実際に書かれている文言から拾う。書かれていないことは補わず、必要なら「メモに記載なし」とする。
- 複数のコミットや複数の文書の話題を混ぜて、1つの変化として組み立てない。変化はコミット／文書ごとに分けて書く。
```
