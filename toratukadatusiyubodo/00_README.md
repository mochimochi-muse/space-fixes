### C. Space 改修が 11/26 に間に合わない場合の暫定の扱い
- ジョブ側（A-2・A-3）は予定どおり入れる。ジョブはダッシュボードに触らないので、改修の有無に関係なく安全。
- もちは 04 の6章「暫定のやり方」で反映する。要点：
  1. getSnapshot の結果を「元の控え」として持つ。
  2. その日に反映する値ファイルをまとめ、該当の項目だけを書き換える（予定の並び順と note は特に触らない）。capturedAt は今の時刻にする。
  3. saveSnapshot は**まとめて1回だけ**。
  4. getSnapshot で読み直し、書き換えた項目と capturedAt 以外が元の控えと同じか比べる。違えば正しい全体で保存し直し、1行報告。
- 11/26 の「解約済み（11/26）」の更新も同じやり方で行う（cadence はまだ無いので書かない）。
- 週次棚卸し（11/29）は、05 の本文なら部分更新の操作が無いことを検知して値ファイルに残すので、全体の上書きは起きない。もちが暫定のやり方で反映する。

## 3. 用語（平易な説明）
- **部分更新**：ダッシュボード全体ではなく、1つの欄（例：Claude Pro のカードだけ）を変える操作。他の欄に触れないので、関係ない欄が崩れる事故が起きない。
- **値ファイル**：ジョブが測った値を書き残す小さなファイル（JSON）。もちが反映したら「反映済み」の置き場へ移す。反映できなければ残るので、そのまま「退避」になる。
- **正本**：その情報の「元」として信じる場所。予定は MEMORY.md の5節、ジョブ一覧は実際の cron の登録。
- **cadence（更新の頻度）**：カードが毎日更新されるもの（daily）か、手で時々更新するもの（manual）か。古さで色を変えるかどうかの判断に使う。
