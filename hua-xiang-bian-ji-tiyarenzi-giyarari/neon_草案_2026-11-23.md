# 静的ギャラリーページ（index.html）改修依頼

## 0. 改修の前提と絶対遵守ルール
- 単一ファイル構成の維持：公開ページはこれまで通り単一の index.html とし、総作品数・シリーズ数はデータから自動計算する。件数は手入力しない。件数照合手順：改修前の index.html から全作品の id 一覧と総件数を抽出して基準リストを保存し、改修後の index.html の作品データと自動照合して件数と全 id が一致してから公開する。※「231件」は改修実施時点の暫定目安としてのみ扱う。
- 既存の作品IDは一切変更・採番し直さない。キュー・★高評価・シリーズ・表示順のすべての紐付けはこのIDを基準にする。
- とした箇所は、実ファイル（index.html）の該当部分を参照して確定させる前提の指示である。

## A. 改修依頼文の草案（ビルダーにそのまま渡せる形）
1. キュー保存を固定キー化する：並び順（配列インデックス）での保存をやめ、作品の id をそのまま固定キーとして保存する。キュー用 localStorage キーは gallery_queue_v2、高評価（★）用は gallery_stars_v1 とする。旧キューは初回表示時に1回だけ自動移行する。移行後は旧データは削除せず gallery_queue_v1_backup として残し、再実行しない。※旧キューが保存されている localStorage キー名と保存形式（配列の例：[0, 5, 12] など）を現行 index.html のJSから確認し、移行スクリプトの読み取り元として明示すること。
2. ライトボックスのフォールバック：原寸画像（full）のパスが無い・空・未設定の作品は、原寸の代わりに通常画像（image）を拡大表示に使う。原寸がある作品は従来通り原寸を使う。原寸も通常画像も存在しない場合はエラー画像ではなく代替表示（「画像がありません」）とし、無限ループしない制御を入れる。※原寸画像の有無の判定方法（full フィールドの有無、空文字判定、別フラグの有無）を現行 index.html から確認し、判定条件を明記すること。
3. 冒頭（ヘッダー）エリアの簡略化：約60字のリード文＋作品総数（自動計算）＋「最新の追加」1行（最新追加作品のシリーズ名とタイトルへのリンク）＋リンク行（「更新履歴」「使い方」「通し方のメモ」）だけにする。現在の約1,250字のリード全文は削除せず、「更新履歴」画面の冒頭に原文のまま残す。更新履歴・使い方・通し方のメモはリンクから開く別画面（モーダル）へ移す。通し方のメモには、各メモに紐付く根拠のシリーズへジャンプするボタンを付け、ボタンを押すとモーダルを閉じて対象シリーズへスクロールする。※現在のリード全文と「通し方のメモ」の具体的な本文、根拠シリーズの対応を現行 index.html から抽出して、依頼文に付録として添付すること。60字リードの具体的な文言は、現行のリード全文の主旨を要約したものを依頼文に提案として入れること（最終確定は利用者確認とする）。
4. シリーズの系統分類と目次：全シリーズを5系統（段階シリーズ／比較・境界実験／自主研究／技法／ストーリー）に分類する。目次は系統ごとに折りたたみ可能（details/summary）とする。シリーズの選択肢（絞り込みのセレクトボックス）も系統で optgroup による区切りを付ける。※現行の全シリーズ名の一覧と、5系統へのマッピング表を現行 index.html から作成し、依頼文に添付すること。未分類のシリーズは、分類を決めてから実装すること。
5. 絞り込みバーと並び順：絞り込みバーは冒頭のすぐ下に配置する。絞り込み条件に加え、並び順の切り替え（セレクト）を追加する。初期値は「新しい順」とする。ただしシリーズ内は段階順のまま維持する（シリーズ内の作品順は「新しい順」に並べ替えない）。スマートフォン表示では絞り込みバー全体を常時表示せず、「絞り込み」ボタンで開閉する形にする。
6. 組み合わせビルダーの移設：組み合わせビルダーは画面下部のキューエリア内のタブとして配置する。ページ上部には、キューエリアへスクロールしてビルダーのタブを開く入口ボタンだけを残す。
7. カード表示の改善：カードの標準表示はコンパクト表示（説明文なし）とする。詳細表示への切り替えボタンを設け、切り替え状態は localStorage に保存して次回表示時も維持する。カードのアスペクト比を統一（例：aspect-ratio: 4/3、実装で確定）し、画像読み込み中のガタつき（レイアウトシフト）を無くす。画面外のシリーズは描画しない（IntersectionObserver による遅延描画／仮想化）ようにする。※現行のカードの縦横比・画像サイズの実態に合わせて aspect-ratio の値を確定させること。
8. サムネイル化：カードと目次に使う画像は、幅約480pxのサムネイルに置き換える。現状は幅1,000〜1,792pxの表示用画像を読み込んでおり、最初の画面で約8.6MB読み込んでいる。サムネイル化により初回読み込みを約0.6MB、全件でも約7MBを目標とする。画像の生成はセクションCの generate_thumbs.py を使用する。※現行の画像パス規則（例：images/xxx.jpg）とサムネイルの出力先・命名規則を、現行のフォルダ構成に合わせて確定すること。
9. 作品データの集約：作品データを、ページ内の目印付きの1か所（例：// === WORKS DATA START === 〜 // === WORKS DATA END === の間の const WORKS = [...]）に1作品1行の形式で集約する。表示ロジック（レンダリング・絞り込み・ソート）は、この WORKS 配列だけを読んで表示する。将来、外部データファイル（works.json など）に分離する場合に、WORKS 配列部分をそのまま外部ファイルに移行できる構造にする。外部データファイルを読み込めるかは未検証のため、まずはページ内集約とする。※現行の作品データの変数名・キー名（id, title, series, desc, image, full 等の実際のプロパティ名）を現行 index.html から確認し、WORKS 配列のキー名をそれに合わせること。作品データの並び順（登録順かシリーズ順か）も確認し、移行時の旧キュー解決の基準配列とする。
10. 作業記録JSONの除外：画像フォルダに混ざっている作業記録JSON（10件）は、index.html 内で文字列検索しても参照が0件であることを確認したうえで、公開側のフォルダから外す（別ディレクトリへ退避）。公開フォルダに残さない。

## B. キュー固定キーの移行設計
### 1. キーの形式と localStorage スキーマ
既存の作品ID（例："w001"、"2026-014" 等、データ内の id フィールド）を正規化した文字列をそのまま固定キーとする。
const toWorkKey = (id) => String(id).trim();
保存先キー設計（バージョンを明示して旧キーと衝突させない）：
・新キュー：gallery_queue_v2　{"version":2,"keys":["id_012","id_045"],"updatedAt":"2026-11-23T16:00:00Z"}
・★高評価：gallery_stars_v1　{"version":1,"keys":["id_003","id_012"],"updatedAt":"2026-11-23T16:00:00Z"}
・移行状態管理：gallery_queue_migration_v2　{"status":"migrated","migratedAt":"2026-11-23T16:00:00Z","droppedCount":0}

### 2. 旧キューの自動引き継ぎ手順（初回のみ）
重要な前提：旧インデックスを解決する際は、必ず「新しい順」ソートをかける前の元データ配列（改修前のページ出現順を保持した配列）を参照する。migrateQueueIfNeeded(orderedWorks, legacyStorageKey) という関数で、旧キーから読み取ったインデックス配列を元データ配列の順序で作品IDに変換し、新キー gallery_queue_v2 に保存する。移行済みフラグ（gallery_queue_migration_v2）があれば再実行しない。旧データは gallery_queue_v1_backup として残す。

### 3. 失敗時・異常系の扱い
・JSON破損・型不正：safeParseJSON で例外捕捉 → gallery_queue_v1_backup_corrupted に生文字列を退避し、status:"failed_invalid_format" を記録して空キューで起動。目的：ページ全体のJS停止および毎回のエラー再発を防止。
・範囲外インデックス（削除済み・負数・件数超過）：該当要素のみスキップして有効な作品IDだけで新キューを構築し、初回のみトースト通知を表示。目的：有効なキュー項目まで道連れで消えるのを防止。
・旧データにIDとインデックスが混在：validIdSet との一致判定を優先し、一致しなければ数値インデックスとして解決。目的：過去の途中改修で混在していた場合でも救済。
・重複エントリ：seen セットで初出順を維持したまま重複排除。目的：キュー内の重複表示防止。
・ブラウザのStorage制限・プライベートモード：localStorage.setItem を try-catch でラップし、メモリ上の状態のみで動作継続。目的：Safariプライベートブラウズ等での例外落ち防止。

## C. サムネイル生成スクリプトの叩き台
### 出力先・命名規則の設計
入力元（例）：./images/（例：./images/series_a/001.jpg）
出力先：./images/thumbs/（例：./images/thumbs/series_a/001.webp または.jpg）
メリット：作品IDやパスから機械的にサムネイルパスを生成でき、元のファイル名を汚さず、公開フォルダからサムネイル一式だけを削除・再生成するのも容易。
容量試算：231件で合計7MB以内にするには1枚あたり平均 約30KB以下が目安。幅480pxのWebP（quality=80）または最適化JPEG（quality=78, progressive）で、透明度・縦長・横長画像も崩れないようにする。
### Python + Pillow スクリプト（generate_thumbs.py）の要旨
・元画像は一切変更・上書きしない（読み取り専用で扱い、出力先が入力先と重複する場合は停止）。
・幅480pxにリサイズする。元画像が480px以下の場合は拡大せず、そのままの幅で出力する。
・WebP（quality=80）またはJPEG（quality=78, progressive, optimize=True）で保存し、EXIF回転を補正する（ImageOps.exif_transpose）。
・出力先は入力の相対パスを維持した./images/thumbs/ 配下。既存のサムネイルがある場合はスキップ（--force で再生成）。
・処理結果を件数・合計容量・失敗一覧として出力する。
※スクリプト全文はチャット内のコードブロックにある（ダウンロード可能）。

## D. 移行手順（段階分け）・公開前チェックリスト・壊れやすい点
### 1. 移行手順（5段階）
Phase 0：現状保全と事前照合（準備）— 現行 index.html と画像フォルダ一式をバックアップ。現行 index.html から全作品の id 一覧と総件数を抽出して基準リストを保存。画像フォルダ内の作業記録JSON（10件）のファイル名が index.html 内で文字列検索しても0件ヒットであることを確認し、公開対象外ディレクトリへ退避。
Phase 1：サムネイル生成と容量検証 — generate_thumbs.py をローカルで実行し、幅480pxサムネイルを生成。合計容量が約7MB前後に収まっていること、縦長・横長・透過画像の崩れやEXIF回転ズレがないことを目視確認。
Phase 2：ビルダーへの改修依頼実行（データ集約＋UI改修）— セクションAの改修依頼文（および確認済みの変数名・キー名・シリーズ系統マッピング表）をビルダーへ渡して新しい index.html を生成。
Phase 3：ローカル検証（データ整合性・旧キュー移行テスト）— 生成された index.html の作品件数・ID集合を Phase 0 の基準リストと自動照合。DevToolsのApplicationタブから旧形式のキュー配列（例：[0, 5, 10, 999]）を手動注入してリロードし、正しい作品IDへ自動移行されること・範囲外インデックス（999）が安全に除外されることを検証。
Phase 4：公開反映と事後確認 — サムネイルフォルダと改修版 index.html を公開環境へ反映（作業記録JSON 10件が公開側に含まれていないことを再確認）。実機（PCおよびスマートフォン）で初回通信量・ライトボックス・モーダル遷移を確認。

### 2. 公開前チェックリスト
[] データ保全：改修前後で作品総数と全 id の完全一致を確認したか
[] 非公開ファイル除外：作業記録JSON（10件）が index.html から未参照であり、公開フォルダから除外されているか
[] キュー移行：旧インデックス形式のキューが初回リロードで id 配列へ変換され、2回目以降再実行されないか
[] ★高評価：★の付与・解除・絞り込みがリロード後も保持されるか
[] ライトボックス：原寸あり作品は原寸が、原寸なし作品は通常画像がエラーなく拡大表示されるか
[] 冒頭・別画面：冒頭が「約60字リード＋件数＋最新の追加1行＋リンク行」に収まり、約1,250字の旧リード全文が「更新履歴」内に原文のまま残っているか
[] 通し方のメモ：メモ内の各シリーズジャンプボタンでモーダルが閉じ、対象シリーズへ正確にスクロールするか
[] 目次・絞り込み：5系統の折りたたみ目次、初期値「新しい順」、シリーズ内「段階順」維持、スマホでの「絞り込み」ボタン開閉が動作するか
[] 組み合わせビルダー：画面下部のキュー内タブに収まり、ページ上の入口ボタンから直接開けるか
[] 表示・通信量：コンパクト表示が初期値で詳細切り替えが保存されるか、読み込み時のガタつきがないか、初回通信量が約0.6MB前後に収まっているか

### 3. 壊れやすい点の洗い出し
1. ビルダー出力時のデータ途中省略：約326KBの index.html を一度に処理させると、出力トークン制限等で作品データが途中で省略・短縮される。回避策：改修前後での「総件数・全ID一致チェック」を必須ゲートにし、必要ならデータブロックだけスクリプトで機械的に流し込む。
2. 画面外シリーズの未描画とジャンプ機能の競合：DOM未描画のシリーズに対して「目次クリック」や「通し方のメモのジャンプボタン」が scrollIntoView を実行し、移動に失敗する。回避策：ジャンプ要求時に「対象シリーズを即座に強制描画 → 系統折りたたみ展開 → スクロール実行」を1関数に集約する。
3. 旧キュー移行時の基準配列順のズレ：「新しい順」ソート済みの配列に対して旧インデックスを引いてしまい、移行初回から別作品を指す。回避策：移行処理は必ず「index.html 記載順（改修前と同一順）の生データ配列」に対して実行し、その後に表示用ソートを行う。
4. 組み合わせビルダー移設に伴うID衝突・イベント断絶：ページ本体からキュー内タブへDOMを移した際、旧ボタンのイベントや関連UIとの連動が切れる。回避策：ビルダーの入出力インターフェース（キューへの追加関数など）を固定キー（id）基準に統一する。
5. ライトボックスのフォールバック無限ループ：原寸画像も通常画像もパス切れだった場合、onerror が繰り返し発火する。回避策：img.dataset.fallbackTried="1" フラグを立て、1回フォールバックしたら再試行しない制御を入れる。

## E. 前提にしたこと・確認が要ることの一覧
・データ構造／作品データの格納形式：前提は index.html 内のJS配列またはJSONとして全件記述されている。要確認は現在の変数名・キー名（id, title, series, desc, image, full 等の実際のプロパティ名）と、データの並び順（登録順かシリーズ順か）。
・シリーズ分類／5系統へのマッピング：前提は全シリーズが「段階シリーズ／比較・境界実験／自主研究／技法／ストーリー」のいずれかに過不足なく分類可能。要確認は現行全シリーズ名の一覧と、各シリーズが5系統のどれに該当するかの対応表。
・画像パス／フォルダ構成と拡張子：前提は画像は専用ディレクトリ配下にあり、WebPまたは元の拡張子でサムネイル参照を組み立てられる。要確認は現在の画像パス規則（例：images/xxx.jpg）、原寸画像の有無の判定方法（別フィールドか、ファイル名規則か、存在しない作品の一覧）。
・ストレージ／旧キューの保存キーと形式：前提は localStorage に配列インデックスのJSON配列として保存されている。要確認は現行の localStorage キー名、保存値のデータ構造、すでに使われている他の localStorage キーとの重複有無。
・既存機能／組み合わせビルダーの仕様：前提は選択した作品や条件を組み合わせてキューへ送る機能として存在している。要確認はビルダーの具体的な入力項目・出力動作・キューとの連携ロジック。
・ホスティング／公開環境とビルド方式：前提は静的ファイル配信で.webp および aspect-ratio / IntersectionObserver が利用可能。要確認は配信サーバーのMIMEタイプ設定（.webp 対応）、今後の更新運用でHTMLと画像フォルダをどう同期アップロードするか。
