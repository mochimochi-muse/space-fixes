## 適用の順序

① **スクリプトを常設場所へ写す**
```sh
mkdir -p ~/workspace/system-setup/space-backup
cp ~/workspace/audit/space-fixes/backup/export_space_data.py ~/workspace/system-setup/space-backup/
sha256sum ~/workspace/system-setup/space-backup/export_space_data.py   # ed8f78cd… と同じなら良い
```
写す前に `~/workspace/system-setup/space-backup/` が既に無いことを確かめる（今回は system-setup の中を見ていない）。

② **手で1回試す**（本番の書き出し先へ。これで最初の日曜より前に space-data/ ができる）
```sh

TZ=Asia/Tokyo python3 -I ~/workspace/system-setup/space-backup/export_space_data.py --restore-test ~/workspace/backups/stage/space-data
```
1つめが「全部成功しました。」（終了コード0）、2つめが4つとも「[一致]」なら良い。行数は下の「試し実行の結果」とほぼ同じはず（その後にSpaceへ書き込みがあれば増えている）。
先に `~/workspace/backups/stage/` に `space-data` という名前のものが無いことを確かめる。

③ **ジョブ本文に追加する**：live のジョブ本文を開き、11-08 のコピーと突き合わせてから、`01_週次バックアップジョブ改訂文案.md` の「3.」の文面を差し込む（ずれていたときの扱いは同文書の「5.」）。

④ **復旧メモ等に追記する**：`01_…` の「2-2」（復旧メモ.md、必要）・「2-3」（setup.sh、確認の1行だけ・任意）・「2-4」（復元手順.md、推奨）。

⑤ **次の日曜（2026-11-29 08:12）の実行結果を確かめる**
- 報告に「Spaceデータ：4件書き出し済み（…）」の1行が付いているか。
- できた tar.gz に space-data が入っているか：`tar tzf ~/workspace/backups/mochi-backup-2026-11-29.tar.gz | grep space-data`（`workspace/backups/stage/space-data/manifest.json` と4つの `<slug>.json` が並べば良い）。

## 試験の結果（/tmp に作った「偽のSpace置き場」で）
本物の ts-spaces には触れずに、`--spaces-root` で /tmp の偽の置き場を指して確かめた。試験の出力（backup/_test/）と偽の置き場は、試験の最後に消した。

1. **安全のために止まるか**（6通り、すべて終了コード2・何も作らない）
   - 出力先が偽の置き場の中／偽の置き場そのもの／偽の置き場を含む /tmp → 止まった
   - 出力先が「空でなく、前回の書き出しでもない」フォルダ（backup/ 自体）→ 止まった
   - 復元先が偽の置き場の中 → 止まった
   - 復元の試しに存在しないフォルダ → 日本語の説明で止まった
   - 偽の置き場の中身は前後で同じ、作業フォルダの作りかけも残らなかった。
2. **WAL（書きかけの変更を -wal に持つ仕組み）の落とし穴**：Spaceの代わりのプログラムがデータベースを開いたまま、本体にまだ入っていない5行を -wal に持たせた状態で確かめた。
   - app.db だけを写して開くと 3行（-wal の5行が抜ける）→ **-wal も写す必要がある**。スクリプトは写している。
   - app.db と -wal を写して読み取り専用で開くと 8行（正しい）。-shm は写さなくてよい（開いたときに作り直される）。
   - 同じ写しを `immutable=1` という開き方にすると 3行（-wal を無視してしまう）→ この開き方は使ってはいけない。スクリプトは使っていない。
   - 読み取り専用で開いても、開いたフォルダには -wal・-shm が**新しくでき、残る**。元のフォルダで開くとSpaceの置き場が汚れるので、**写しを一時フォルダに取ってから開く**作法が必要（スクリプトはそうしている。本物の写しでも同じことが起きるのを確認した）。
   - スクリプト全体で書き出すと、8行が書き出された。書き出しの前後で、元のフォルダのファイルは大きさ・更新時刻とも変わらなかった。
3. **書き込みが続いている最中**：3ミリ秒おきに書き込み続けると、5回中4回は「写している間に元が書き換わり続けたため、5回写し直しても揃いませんでした」で失敗した（安全な失敗。他のSpaceは書き出される）。0.2秒おきの書き込み（-wal が約4MB）の試験は1回だけで、1回目の写しで揃い、点検（quick_check）も ok だった。
4. **失敗したときの引き継ぎ**：写している間に書き換わり続けるよう細工したSpaceは、2週続けて失敗しても、最後に成功した回の分が `<slug>.previous.json` として残り続けた。復元の試しはその前回分で「[一致]」を出しつつ、終了コード1で失敗を知らせた。`--restore` も前回分から作り直せた（「注意：…前回の控えから作り直します」と表示）。2回だけ書き換わるよう細工したSpaceは、3回目の写しで成功した。
5. **app.db が無いSpace**：そのSpaceだけ失敗（「…app.db が見つかりません」「引き継げる前回の書き出しはありません」）、他の3つは書き出された（終了コード1）。
6. **復元の上書き防止**：同じ場所へもう一度 `--restore` すると「既にあります。上書きはしません」で止まった（終了コード2）。復元で作られるのは app.db 1つだけ。
7. **途中で止まった跡の片づけ**：2時間前の作業フォルダの残り（`.out1.new-…`・`.out1.old-…`）は次の実行で消え、作ったばかりのものは消さなかった。
8. /tmp に一時フォルダ（`s3_backup_…`）が残らないことを毎回確かめた。

## スクリプトの使い方（平易に）

どれも `python3 -I <スクリプトの場所> …` の形で動かします（`-I` は、周りの設定や同じフォルダのファイルに左右されずに動かすための付け足し）。日本時間で記録したいときは前に `TZ=Asia/Tokyo` を付けます。

- **書き出す**：`--out <書き出し先のフォルダ>`
  - 4つのSpaceのデータを、Spaceごとに1つのJSONファイルへ書き出し、目録の `manifest.json` を作ります。
  - 書き出し先のフォルダは**毎回まるごと入れ替わります**。このフォルダには他のものを置かないでください（置いてあると、次の書き出しで消えます。最初から他のものが入っているフォルダを指定した場合は、書かずに止まります）。
  - Spaceの置き場（~/workspace/ts-spaces/）と重なる場所を指定すると、何もせずに止まります。
- **復元の試し**：`--restore-test <書き出したフォルダ>`
  - 書き出したJSONから、一時フォルダでデータベースを作り直し、中身と行数が書き出しと同じかを確かめます。何も残しません。
- **復元（本番）**：`--restore <書き出したフォルダ> --slug <Spaceのslug> --to <新しく作るファイル>`
  - 指定した場所にデータベース（app.db）を作り直します。既にあるファイルは上書きしません。Spaceの置き場の中には作りません。
  - それをSpaceに戻すのは、本人の了承を得て、Spaceを止めてから、古い app.db・app.db-wal・app.db-shm を退避した上で行います（手順の細部は未確定）。
- **終わったときの番号（終了コード）**：0＝全部成功／1＝失敗したSpaceがある（他は書き出し済み）／2＝安全のため、または指定の誤りで止めた（何も書いていない）。
- **出てくるファイル**：
  - `manifest.json`：目録。書き出し日時、Spaceごとの成否・表ごとの行数・JSONの大きさと指紋（SHA-256）・元の app.db の大きさと更新時刻・写しの指紋・かかった時間など。
  - `<slug>.json`：Spaceのデータ本体。`tables` の下に表ごとに、表の作り（`create_sql`）・列の名前（`columns`）・行数（`row_count`）・全部の行（`rows`、1行ずつ「列名: 値」の形）が入っています。日本語はそのまま読めます。`hidden_rowids` は、表に見えない行番号を元どおりにするための控えです。画像などの値があれば `{"$blob_base64": …}` という印で入ります（今の4つには無い）。
  - `<slug>.previous.json`：そのSpaceの書き出しに失敗した回だけできる、前回成功した分の控え。
- **Spaceが増えたら**：スクリプトの上の方にある `SPACES` の一覧に、`("<slug>", "<表示名>"),` を1行足します。足さないと、そのSpaceは控えられません。

## 直した点（前回の下書き 23,630バイト → 検収版 28,974バイト）

検収で「問題なし」と確かめた点（変えていない）：元の app.db を開かない（一時フォルダへ写してから読み取り専用で開く）／-wal も写し、-shm は写さない／写している間の書き換わりを大きさ・更新時刻で見つけて写し直す（最大5回）／Spaceの置き場と重なる出力先・復元先は止まる（終了コード2）／対象4 Spaceの slug が正しい／JSONは日本語そのまま（ensure_ascii=False）・表ごと・行ごと・列名つき／件数・書き出し日時・元の大きさと更新時刻・写しとJSONの指紋がある／書き出すたびにJSONから作り直して一致を確かめる／標準ライブラリだけで動く。

直した点：
1. **失敗したときに、最後の良い控えを消さないようにした。** 下書きは、Spaceの書き出しに失敗すると、そのSpaceの前回分ごとフォルダを入れ替えて消していた。直した版は、前回までに成功した分を `<slug>.previous.json` として引き継ぎ、続けて失敗しても引き継ぎ続ける。復元の試し・復元もこの前回分を使える。
2. **書き出しフォルダの権限を、周りのフォルダと同じにした。** 下書きは作業フォルダを「所有者だけが読める」作り方（0700）で作っていたため、書き出しフォルダも所有者専用になっていた（試し実行で気づいた）。いったん後から権限を付け直す直し方を試したところ、親フォルダのグループを引き継ぐ印（setgid）が外れ、中のファイルのグループが周り（nogroup）と違う root になったので、その方法はやめ、作業フォルダを「ふつうのフォルダ作成」で作る形にした。今は周りと同じ `drwxrws--- root:nogroup`、ファイルも `root:nogroup` になっている。
3. **途中で止まった跡を片づけるようにした。** 強制的に止められて作業フォルダ（`.<名前>.new-…`・`.<名前>.old-…`）が残った場合、1時間より古いものは次の実行で消す。
4. **目録（manifest.json）が無い・壊れているとき、日本語の説明で止まるようにした**（終了コード2）。下書きは Python のエラー表示のまま終わっていた。
5. **古いフォルダを消すのに失敗しても、書き出しの成功を失敗扱いにしないようにした**（消し残しは3.の片づけで消える）。
6. **Spaceごとの書き出し時刻を目録にも残すようにした。** 引き継いだ前回分の日時が、JSONの中の日時と食い違わないようにするため。
7. 説明書きを足した：読み取り専用で開く関数に「写しにだけ使う（元で開くと -wal・-shm ができる）」「immutable=1 は付けない（-wal が無視される）」の注意、冒頭の説明に「1世代で入れ替え」「前回分の引き継ぎ」「日本時間で残すなら TZ=Asia/Tokyo」。
